# Token signing key rotation

Berth issues **RS256** registry JWTs from the **app** container. The **registry** validates them using `REGISTRY_AUTH_TOKEN_ROOTCERTBUNDLE` — a PEM file that can hold **multiple concatenated certificates** for zero-downtime rotation.

Every issued token includes the signing cert in the JWT `x5c` header (in addition to the bundle), which matches Distribution `registry:3` validation behavior.

## Key material map

| Role | App env | Registry mount | Notes |
|------|---------|----------------|-------|
| Private signing key | `TOKEN_SIGNING_KEY` or `TOKEN_SIGNING_KEY_PATH` | — | Never mount into registry |
| Public cert (active signer) | `TOKEN_CERT` or `TOKEN_CERT_PATH` | — | Embedded in JWT `x5c` |
| Trust bundle | — | `REGISTRY_AUTH_TOKEN_ROOTCERTBUNDLE` → `rootcert.pem` | One or more PEM certs, concatenated |

Default compose paths:

| Container | Path |
|-----------|------|
| app | `/etc/berth/token/signing-key.pem`, `/etc/berth/token/signing-cert.pem` |
| registry | `/etc/registry/certs/rootcert.pem` |

Dev keys are generated by [`docker/token/generate-keypair.sh`](../docker/token/generate-keypair.sh). **Do not use dev keys in production.**

## Rotation procedure (overlap window)

Goal: switch signing keys without rejecting in-flight tokens. Default `TOKEN_TTL_SECONDS` is **300** (5 minutes); wait at least that long between steps 3 and 4.

### Step 1 — Generate a new keypair

On a secure workstation:

```bash
./docker/token/generate-keypair.sh   # dev helper — use unique paths in production

# Or manually:
openssl genrsa -out new-signing-key.pem 2048
openssl req -new -x509 -key new-signing-key.pem -out new-signing-cert.pem \
  -days 825 -subj "/CN=berth-token-issuer" -sha256
```

Keep `new-signing-key.pem` secret.

### Step 2 — Append new cert to the registry bundle

The bundle file (`rootcert.pem`) must contain **both** the old and new public certificates:

```bash
cat old-signing-cert.pem new-signing-cert.pem > rootcert.pem
```

Deploy the updated bundle to the registry mount (`/etc/registry/certs/rootcert.pem`) and restart **registry only**:

```bash
docker compose -f docker/compose.yml restart registry
```

The registry now trusts JWTs signed by either key.

### Step 3 — Switch app to the new private key

Point the app at the new key and cert (env or mounted files):

```yaml
app:
  environment:
    TOKEN_SIGNING_KEY_PATH: /path/to/new-signing-key.pem
    TOKEN_CERT_PATH: /path/to/new-signing-cert.pem
```

Or inline PEM via `TOKEN_SIGNING_KEY` and `TOKEN_CERT`.

Restart **app**:

```bash
docker compose -f docker/compose.yml restart app
```

New tokens are signed with the new key and include the new cert in `x5c`. Old tokens (signed with the previous key) remain valid until they expire, because the old cert is still in the bundle.

### Step 4 — Wait for token TTL

Wait at least **`TOKEN_TTL_SECONDS`** (default 300s) after step 3. Optionally wait longer if you increased TTL.

No registry pushes should fail during this window — Docker clients automatically request a fresh token on `401`.

### Step 5 — Remove old cert from bundle

Edit `rootcert.pem` to contain **only** the new certificate (remove the old PEM block). Restart **registry**:

```bash
docker compose -f docker/compose.yml restart registry
```

### Step 6 — Securely retire the old private key

Delete or archive the old private key. Update your secrets backup.

## Production key delivery

| Method | App | Registry bundle |
|--------|-----|-----------------|
| Docker secrets / mounted files | `TOKEN_SIGNING_KEY_PATH`, `TOKEN_CERT_PATH` | Volume mount for `rootcert.pem` |
| Environment | `TOKEN_SIGNING_KEY`, `TOKEN_CERT` (PEM with `\n` or real newlines) | Mount bundle file updated by your deploy pipeline |

The production image bakes in dev keys at build time ([`docker/Dockerfile`](../docker/Dockerfile)); override with env or bind mounts in production compose overrides.

## Verification

After rotation:

```bash
docker login <your-host>
docker pull <your-host>/some-project/some-repo:tag
```

Check app logs for token errors. In the portal, confirm catalog and push still work.

## Emergency rollback

If new tokens fail validation:

1. Revert app to the previous `TOKEN_SIGNING_KEY*` / `TOKEN_CERT*`
2. Ensure `rootcert.pem` still includes the cert matching the active signer
3. Restart app and registry
